# Agent evaluation, round 1 (2026-10-02)

The 16 scenarios below were written by the author, who also knows the expected answer of each, so these are test results on the author's own scenarios and not an independent benchmark.

Setup: 6 LLM agents, each with only `tf.py` (persistent TopicForge MCP server
via broker) and a user question; no file access. Live Cyclone/Dust buses from
examples 00, 06, 07, 10, 11, 13 under --hold.

## Accuracy

| Scenario | Correct? | Notes |
|---|---|---|
| 00 typo topic | yes | found `batery` via raw DCPSSubscription |
| 06 late joiner | yes, 3/3 | inferred the both-VOLATILE case TopicForge cannot report, from raw QoS |
| 07 deadline A/B | yes | said honestly it cannot measure the real rate |
| 10 driver swap | yes, 3 causes | also spotted the Dust/Cyclone type_id difference inside _raw_text |
| 11 wiring | yes | Dust participant flagged unnamed/unknown honestly |
| 13 deadline | yes | values found only in _raw_text |

6/6 correct, but every agent had to parse a Python repr (`_raw_text`) and
join GUID prefixes by hand. Correctness came from the agents' effort, not
from TopicForge's structure.

## Findings (how many agents raised it)

F1 (6/6) No endpoint view. QoS, participant link, type id only in `_raw_text`.
F2 (5/6) Mismatch report: no requested/offered values, no participant names, no reason.
F3 (4/6) Unmatched endpoints, near-miss topic names, same-topic type_id differences: not detected.
F4 (4/6) Timestamps useless: first_seen_ns = poll time, equal for all; builtin timestamp_ns 0.
F5 (5/6) DDS-only mode: list_topics/get_topic_info error; health_check "live" + ros none confusing; no flag for payload decoding off.
F6 (4/6) Descriptions: internal history noise ("8-tool ceiling break #3"); domain_id semantics unclear; bare topic names undocumented.
F7 (4/6) peek on a user topic returns count 1 placeholder; topic_metrics all null; looks like data / "no data".
F8 (3/6) No completeness signal on builtin peeks (count vs total).
F9 (2/6) TopicForge's own participant and builtin readers not flagged.
F10 (2/6) Deadline infinite shown as INT64_MAX.
F11 (2/6) vendor "unknown" without a reason.
F12 (3/6) detect_qos_mismatches: no policies_checked / pairs_checked; "[]" over-trusted (Partition, Liveliness, Ownership unchecked).
F13 (1/6) topic_metrics frequency_hz_declared null although the writer deadline is in discovery.

# Round 2 (live failures, critical blind spots)

| Scenario | Result | Root problem in TopicForge |
|---|---|---|
| restart_loop | WRONG: 1 restart reported, truth 3 | lifecycle only updated when a tool is called; events timestamped at poll time |
| crash_live | diagnosis right, time wrong (said 46.6 s alive, truth ~29 s) | lost event dated at poll time |
| partition_split | right, but only from _raw_text; detect_qos_mismatches pointed at Reliability only | Partition ignored: misleading root cause |
| hung_estop | honest 60% inference | no writer liveliness / last activity visible: hung == healthy |
| big_bus (7 seeded) | 7/7 found, 1 misattribution (reader given to wrong program by GUID prefix) | 3/7 only via raw repr (Liveliness, Ownership, Partition); ~60k chars read, 40k avoidable |

New findings:
F14 (critical) Lifecycle is poll-driven: restarts and short-lived participants are missed, times are wrong. Needs continuous background discovery tracking with DDS source timestamps.
F15 (critical) detect_qos_mismatches misses Partition (and gives a misleading Reliability root cause when partitions differ), Liveliness, Ownership.
F16 (high) No endpoint-level liveliness / activity: a hung writer looks healthy.
F17 (high) Manual GUID-prefix attribution causes real errors: participant_name must be in every endpoint/mismatch output.
F18 (medium) list_participants fields (status, first_seen_ns, last_seen_ns, seen_count) undocumented in the description; no observing_since / now.
F19 (medium) Output volume: builtin peeks dump huge repr strings (14k chars), list 12k chars.
